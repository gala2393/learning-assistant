## 一、资料上传与解析

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/material/` 目录（`MaterialController.java`、`MaterialService.java`、`MaterialParseService.java`、`ChunkingService.java`、`PdfParseService.java`、`DocxParseService.java`、`PptxParseService.java`）
> 📄 **前端文件**：`frontend/src/components/workspace/MaterialsPage.tsx`、`MaterialUploadForm.tsx`、`MaterialCard.tsx`、`frontend/src/api/materials.ts`

### 1.1 整体流程总览

```
用户选择文件 → 前端分片上传 → 后端接收 → 文件格式解析 → 语义分块 → 生成 Embedding → 存入数据库
```

整个流程是**异步**的：用户上传完文件后可以继续做其他事，后端在后台处理，前端每 1.5 秒轮询一次状态。

### 1.2 分片上传（大文件支持）

#### 为什么要分片？

直接上传大文件（比如 200MB 的 PDF）可能会因为网络波动导致上传失败。分片上传把文件切成小块（每块 5MB），即使某一块失败了，只需要重传那一块，不用从头开始。

#### 上传流程

```
第 1 步：创建上传会话
  前端 → POST /api/materials/upload-sessions
  后端创建：
    - LearningMaterialEntity（资料记录，状态 PENDING）
    - MaterialUploadSessionEntity（上传会话，状态 UPLOADING）
    - 在磁盘上创建 .parts 临时目录

第 2 步：逐片上传
  前端把文件按 5MB 切片：file.slice(start, end)
  每片 → POST /api/materials/upload-sessions/{sessionId}/chunks
  后端将每片保存为 000000.part、000001.part...
  可选：每片附带 SHA-256 校验和，后端验证完整性

第 3 步：自动触发处理
  当所有片都上传完成（uploadedChunks >= totalChunks）：
  后端将 session 状态设为 PROCESSING
  在后台线程中执行 processUploadSession()
```

#### 前端重试机制

```typescript
// 每片最多重试 3 次，每次间隔递增（600ms × 尝试次数）
async function uploadChunkWithRetry(sessionId, chunkIndex, chunk, totalChunks) {
  for (let attempt = 1; attempt <= 3; attempt++) {
    try {
      await api.post(`/materials/upload-sessions/${sessionId}/chunks`, formData)
      return // 成功
    } catch (e) {
      if (attempt === 3) throw e
      await sleep(600 * attempt) // 等 600ms、1200ms
    }
  }
}
```

#### 断点续传

如果用户刷新页面或网络断开，重新上传时，前端会查询会话已上传的片数（`uploadedChunks`），从断点处继续：

```typescript
// 从已上传的片数开始，跳过已完成的
for (let i = session.uploadedChunks; i < totalChunks; i++) {
  await uploadChunkWithRetry(sessionId, i, file.slice(...), totalChunks)
}
```

### 1.3 文件格式解析

后端收到文件后，根据文件类型调用不同的解析器：

#### PDF 解析

使用 **Apache PDFBox** 库逐页提取文本：

```
1. 如果 PDF 超过 64MB，先用 Ghostscript 压缩（144 DPI 降采样）
2. 用 PDFBox 加载 PDF
3. 逐页提取文本（PDFTextStripper，按位置排序）
4. 如果某页提取不到文字（扫描件）：
   - 将页面渲染为 PNG 图片（144 DPI）
   - 用 Tesseract OCR 识别文字（支持中英文）
   - 图片标记为 [[material-image:page-N.png]]
5. 每一页作为一个 ParsedBlock(text, pageNo, "Page N")
```

#### Word 解析（DOCX）

DOCX 文件本质上是一个 **ZIP 压缩包**，里面包含 XML 文件。项目不使用 Apache POI，而是直接解压 ZIP 读取 XML：

```
1. 用 ZipFile 打开 .docx
2. 读取 word/document.xml
3. 用正则提取 <w:p>...</w:p>（段落），再提取 <w:t>（文本）
4. 提取 <w:tbl>...</w:tbl>（表格），格式化为 "cell1 | cell2 | cell3"
5. 从 word/media/* 提取图片，保存到资源目录
6. 图片位置插入 [[material-image:文件名]] 标记
```

#### PPT 解析（PPTX）

和 DOCX 类似，PPTX 也是 ZIP + XML：

```
1. 用 ZipFile 打开 .pptx
2. 找到所有 ppt/slides/slideN.xml，按页码排序
3. 每页提取 <a:t> 标签中的文本
4. 通过 _rels/slideN.xml.rels 找到引用的图片
5. 每张幻灯片作为一个 ParsedBlock(text, slideNo, "Slide N")
```

#### 纯文本（TXT/MD/HTML）

```
1. 检测编码：先看 BOM（UTF-8/UTF-16LE/UTF-16BE），再尝试 UTF-8，最后 GB18030
2. 如果是 HTML：用正则去除 <script>、<style>、<noscript>、注释、所有 HTML 标签
3. 解码 HTML 实体（如 &amp; → &）
```

### 1.4 语义分块（Chunking）

#### 为什么要分块？

一份资料可能有几十页甚至几百页，直接把整份资料给 AI 处理不现实。需要切成小块（chunk），每块 300-800 字符，后续检索时只取出相关的块。

#### 分块算法

```
输入：解析后的文本
输出：文本块列表

1. 按双换行（\n\n）拆分成段落
2. 遍历每个段落：
   a. 如果当前段落超过 800 字符：
      - 先把缓冲区中的内容作为一块输出
      - 按句子（。！？!?.;；）拆分这个长段落
      - 句子也超长？按逗号等标点做软切分，找不到则硬切
   b. 如果缓冲区 + 当前段落不超过 800 字符：
      - 追加到缓冲区
   c. 如果加了会超：
      - 缓冲区内容作为一块输出，清空缓冲区
      - 当前段落放入缓冲区
3. 缓冲区剩余内容作为最后一块
4. 添加重叠：从第二块开始，拼接前一块的尾部（120 字符）
   - 优先在句末标点处截断，保证语义连贯
```

**重叠的意义**：如果一个概念恰好被切到两块的边界，没有重叠的话，检索时可能两块都不完整。120 字符的重叠确保上下文连续。

#### 每个 Chunk 的元数据

分块完成后，为每个 chunk 生成以下附加信息：

| 字段 | 生成方式 | 示例 |
|------|---------|------|
| `summary` | 取第一句话或前 180 字符 | "TCP 是一种面向连接的传输层协议" |
| `keywords` | 词频统计，取前 8 个 | "TCP, 连接, 传输, 协议, 可靠" |
| `hierarchyPath` | 拼接层级 | "计算机网络 > 第3章 > 切片5" |
| `sectionTitle` | 来源章节或自动生成 | "Page 3" 或 "第5切片" |

### 1.5 Embedding 生成

每个 chunk 的文本会被发送到 Embedding 服务，转换为一个**浮点数向量**。

#### 什么是 Embedding？

Embedding 是把文本转换成数学向量的过程。意思相近的文本，向量也相近。比如"TCP 协议"和"传输控制协议"虽然用词不同，但向量会很接近。

#### 支持的 Embedding 模型

| 模型 | 向量维度 | 说明 |
|------|---------|------|
| `text-embedding-v3` | 1536 | OpenAI 兼容格式 |
| `voyage-multimodal-3` | 1024 | 支持文本+图片多模态，使用 Voyage AI API |

系统根据 `EMBEDDING_MODEL` 配置自动选择客户端实现：如果模型名以 `voyage-multimodal-` 开头，使用 Voyage 多模态客户端；否则使用标准 OpenAI 兼容客户端。

#### 实现方式

```
1. 清理文本：去掉 [[material-image:...]] 等标记
2. 计算 SHA-256 作为缓存键（相同文本不重复调用 API）
3. 检查内存缓存（最多 2048 条）
4. 调用 Embedding API（兼容 OpenAI 格式）：
   POST {baseUrl}/v1/embeddings
   Body: { "model": "text-embedding-v3", "input": "文本内容" }
   Response: { "data": [{ "embedding": [0.0123, -0.0456, ...] }] }
5. 将返回的向量序列化为 JSON 字符串，存入数据库
```

#### 配置

```yaml
app:
  embedding:
    enabled: true                           # 开关
    base-url: https://api.voyageai.com      # API 地址（支持 OpenAI/Voyage 兼容接口）
    api-key: sk-xxx                         # API 密钥
    model: voyage-multimodal-3              # 模型名
    top-k: 8                                # 返回最相关的 8 个 chunk
    score-threshold: 0.35                   # 余弦相似度最低阈值
```

### 1.6 存储到向量数据库

如果配置了 Qdrant（一种向量数据库），chunk 的 embedding 会同时存入 Qdrant，后续检索速度更快。如果没有配置，回退到 MySQL 暴力搜索（逐个计算相似度）。

```
Qdrant 存储流程：
  1. 为每个 chunk 生成 UUID 作为 point ID
  2. upsert 到 Qdrant：
     - vector: embedding 数组
     - payload: { materialId, ownerId, chunkId, chunkIndex, pageNo, sectionTitle }
  3. 支持按 materialId/ownerId 过滤搜索
```

## 二、RAG 智能问答

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/rag/` 目录（`RagController.java`、`RagStreamController.java`、`RagService.java`、`QueryExpansionService.java`、`HydeService.java`）
> 📄 **前端文件**：`frontend/src/components/workspace/ChatPage.tsx`、`ChatThread.tsx`、`ChatComposer.tsx`、`frontend/src/api/rag.ts`

RAG（Retrieval-Augmented Generation，检索增强生成）是本项目的核心功能。简单来说就是：**先从资料中找到相关内容，再让 AI 基于这些内容回答问题**。

### 2.1 问答流程总览

```
用户提问
  → 意图检测与查询改写
  → 混合检索（关键词 + 向量 + BM25）
  → 分数融合与重排序
  → 选取 top-K 分块
  → 组装上下文
  → 调用 LLM 生成回答
  → 后处理与装饰
  → 流式返回前端
```

### 2.2 两种问答模式

| 模式 | 说明 | 是否检索资料 |
|------|------|------------|
| **通用模式（GENERAL）** | 直接问 AI，不绑定任何资料 | 否 |
| **资料模式（MATERIAL）** | 绑定一份资料，在这份资料中检索 | 是 |

通用模式直接把问题发给 LLM，跳过所有检索步骤。资料模式才走完整的 RAG 流程。

### 2.2.1 图片与临时资料附件

聊天输入框支持两类附件：

| 附件类型 | 前端处理 | 后端处理 | 历史保存 |
|----------|----------|----------|----------|
| 图片 | `ChatComposer` 压缩为 DataURL，最多 4 张 | 校验 MIME/Base64，作为多模态输入传给 LLM | `rag_question.question_images_json` |
| 临时资料 | 通用模式调用 `/materials/temporary` 抽取文本 | 文本作为本次问答上下文，不创建资料记录 | `rag_question.question_temporary_material_json` |
| 持久资料 | 资料模式走分片上传 | 解析、分块、生成 Embedding | `learning_material` + `material_chunk` |

临时资料常见场景是：用户不想把文件长期放入资料库，只想让 AI 临时参考一下这个文件。它不会参与全局 RAG 检索，也不会出现在资料列表中。

前端展示链路：

```
临时资料上传完成
  → chat-session.temporaryMaterial
  → ChatAttachmentCards 附件卡片
  → TemporaryMaterialPreviewDialog 文本预览
  → 发送问题时进入 ChatRequest.temporaryMaterial
```

图片展示链路：

```
粘贴/选择图片
  → 压缩到最大边长 1280px
  → chat-session.images
  → ChatComposer 缩略图
  → ChatThread 历史消息缩略图
  → ImagePreviewDialog 放大预览
```

### 2.3 查询改写

#### 问题：多轮对话中的指代不清

```
用户：什么是 TCP？
AI：TCP 是一种传输层协议...
用户：它的优缺点是什么？  ← "它" 指什么？
```

如果直接拿"它的优缺点是什么"去做检索，效果很差，因为检索系统不知道"它"是谁。

#### 解决方案

```
rewriteQuestionForRetrieval(question, history):
  1. 从历史消息中提取最近讨论的主题（如 "TCP"）
  2. 判断当前问题是否是追问（短句 + 包含 "它/这个/上述" 等代词）
  3. 如果是追问，将代词替换为主题：
     "它的优缺点是什么" → "TCP的优缺点是什么"
  4. 如果无法替换，简单拼接：主题 + 原问题
```

### 2.4 混合检索

系统使用三种检索方式，取长补短：

#### 方式一：关键词匹配

根据问题的意图，用正则表达式提取关键词：

```
意图识别模式：
  "什么是TCP"      → DEFINITION 意图，关键词 ["TCP"]
  "A和B的区别"     → COMPARISON 意图，关键词 ["A", "B"]
  "X有什么用"      → FUNCTION 意图，关键词 ["X"]
  "X在哪里提到"    → OCCURRENCE 意图，关键词 ["X"]
```

然后在 chunk 文本中搜索这些关键词，根据命中情况和意图类型给分。比如 DEFINITION 意图的 chunk 如果包含"定义""概念"等词会加分。

#### 方式二：向量相似度检索

```
1. 将用户问题通过 Embedding API 转换为向量
2. 计算问题向量与每个 chunk 向量的余弦相似度
3. 余弦相似度公式：
   similarity = (A·B) / (|A| × |B|)
   范围 [-1, 1]，越接近 1 越相似
4. 只保留相似度 >= 0.55 的 chunk
5. 动态阈值：短问题放宽到 0.42，长问题收紧到 0.65
```

#### 方式三：BM25 关键词评分

BM25 是经典的文本检索算法，不依赖向量服务，纯靠关键词频率计算相关性：

```
BM25 公式简化版：
  对于每个查询词 t：
    IDF = log((总文档数 - 包含t的文档数 + 0.5) / (包含t的文档数 + 0.5) + 1)
    TF_norm = (词频 × (K1+1)) / (词频 + K1 × (1 - B + B × 文档长度/平均长度))
    得分 += IDF × TF_norm

  参数：K1 = 1.5（词频饱和），B = 0.75（长度归一化）
```

**中文分词处理**：中文没有空格分隔，BM25 使用 2-6 字的 n-gram 子串作为 token。比如"数据库索引"会被拆成："数据""据库""库索""索引""数据库""据库索""库索引""数据库索""据库索引""数据库索引"。

### 2.5 查询扩展与 HyDE

#### 查询扩展

一个问题可能有多种表达方式。系统用 LLM 生成 2-4 个变体查询：

```
原始问题："TCP 是什么"
扩展查询：
  - "TCP 协议定义"
  - "传输控制协议介绍"
  - "TCP 工作原理"
每个变体都做一次检索，权重 0.82（低于原始查询的 1.0）
```

如果 LLM 不可用，使用本地规则扩展：
- "是什么"类 → 添加 "定义 原理 作用"
- "为什么"类 → 添加 "原因 原理 工作过程"
- "优缺点"类 → 添加 "优点 缺点 限制 适用场景"

#### HyDE（假设性文档嵌入）

```
原始问题："TCP三次握手是什么"
  → 让 LLM 生成一个假设性的答案段落：
    "TCP三次握手是建立TCP连接时，客户端和服务端交换三个报文段的过程。
     第一步客户端发送 SYN，第二步服务端回复 SYN+ACK，第三步客户端发送 ACK。"
  → 用这段假设答案的向量去检索（比用问题检索更接近文档风格）
  → 权重 0.72
```

### 2.6 分数融合与重排序

所有检索结果合并后，按以下公式计算最终分数：

```
最终分数 = 0.55 × 归一化向量分数
         + 0.35 × 归一化BM25分数
         + 0.10 × 查询词覆盖率
```

- **向量分数**：余弦相似度，归一化到 [0, 1]
- **BM25 分数**：归一化到 [0, 1]
- **查询词覆盖率**：chunk 中出现了多少比例的查询关键词

#### 重排序（Reranking）

如果有外部 Reranker 服务配置，融合后的候选 chunk 会发送给 Reranker 做精排。Reranker 是一个专门的模型，它同时看问题和 chunk 内容，给出更准确的相关性分数。

没有外部 Reranker 时，系统使用本地启发式重排。

#### 结果选择（带多样性）

```
selectTopChunks:
  按分数降序排列
  最多取 topK 个（默认 5 个）
  总字符数不超过 10,000
  多样性约束：取了 3 个之后，跳过同一页的重复 chunk
```

### 2.7 上下文组装与 LLM 调用

#### 组装上下文

把选出的 chunk 格式化为给 LLM 的上下文：

```
资料检索片段：

[当前阅读位置，优先依据]
《计算机网络》第 15 页：
TCP 是一种面向连接的、可靠的、基于字节流的传输层通信协议...

[同页或同书补充依据]
《计算机网络》第 16 页：
三次握手过程如下：第一次握手...
```

如果用户在阅读器中选中了某段文字，会被直接作为上下文，不走检索流程。

#### 收集图片

如果 chunk 中包含 `[[material-image:page-3.png]]` 标记，系统会：
1. 从磁盘加载图片
2. 缩放到最大 768 像素
3. Base64 编码
4. 最多附带 5 张图片给 LLM（支持多模态分析）

#### LLM 提示词

系统提示词规定了 AI 的回答规范：

```
资料模式（9 条核心指令）：
1. 优先使用提供的资料片段回答
2. 语言简洁专业，适合学生和教师
3. 引用时注明页码和资料名
4. 必须使用 "原文：《资料名》第 X 页：..." 格式引用原文
5. 如果有"当前阅读位置"标记，优先解释该位置
6. 如果有图片，结合图片内容分析
7. 如果资料不足，明确说"当前资料未覆盖该问题"
8. 不编造不存在的来源
9. 使用自然中文，避免 Markdown 格式
```

**作业模式**额外要求：
- 第一段：完整答案（可直接放入作业）
- 第二段：原文依据（资料名 + 页码 + 原文）
- 第三段：使用提示（如何改写或补充）

### 2.8 流式输出（SSE）

AI 回答不是等全部生成完再显示，而是**一个字一个字地"打"出来**，这就是流式输出。

#### 后端实现

```java
// RagStreamController.java
@PostMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
public SseEmitter chatStream(long currentUserId, ChatRequest request) {
    SseEmitter emitter = new SseEmitter(120_000L); // 120 秒超时

    executorService.submit(() -> {
        try {
            // 1. 发送 "搜索中" 状态
            sendEvent(emitter, "status", Map.of("stage", "searching"));

            // 2. 检索 + 流式生成
            ragService.chatStream(request, (delta) -> {
                sendEvent(emitter, "chunk", Map.of("delta", delta));
            });

            // 3. 发送来源引用
            sendEvent(emitter, "sources", sources);

            // 4. 发送完成信号
            sendEvent(emitter, "done", result);

            emitter.complete();
        } catch (Exception e) {
            sendEvent(emitter, "error", Map.of("message", e.getMessage()));
        }
    });

    return emitter;
}
```

#### SSE 事件类型

| 事件 | 数据 | 说明 |
|------|------|------|
| `status` | `{ "stage": "searching" }` | 开始检索 |
| `chunk` | `{ "delta": "文本片段" }` | LLM 逐字输出 |
| `sources` | `{ "sources": [...] }` | 检索到的来源 |
| `done` | `{ "questionId", "answer" }` | 回答完成 |
| `error` | `{ "message": "错误信息" }` | 出错 |

#### 前端接收

```typescript
// frontend/src/api/rag.ts 的 chatStream 函数
const response = await fetch('/api/rag/chat/stream', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json', 'Authorization': `Bearer ${token}` },
  body: JSON.stringify(payload),

})

  buffer = lines.pop() // 保留不完整的行

  for (const line of lines) {
    if (line.startsWith('event: chunk')) { /* 下一行是文本增量 */ }
    else if (line.startsWith('data: ')) {
      const data = JSON.parse(line.slice(6))
      // 根据事件类型分发到回调函数
    }
  }
}
```

### 3.2 中间栏：文档查看器（ReaderPaper）

两种渲染模式：

**PDF 预览模式**（`previewStatus === 'READY'`）：
- 后端在解析 PDF 时将每页渲染为 PNG 图片

**纯文本模式**（`previewStatus === 'DEGRADED'`）：
- 直接显示 chunk 的文本内容

```
1. 显示当前 chunk 上下文（截取前 70 字符）
2. 支持选中文本提问：
   - 用户在文档中选中 5-500 字符的文字
   - 选中的文字显示在问答面板顶部

3. 推荐问题：
   - 首次加载时调用 /api/rag/suggest-questions
   - AI 根据当前 chunk 内容生成 3 个推荐问题
   - 点击即可直接提问
4. 点击来源引用可跳转到对应的 chunk
5. 可以"在完整聊天中继续"跳转到聊天页面
```

- `?materialId=123` — 当前查看的资料
- `?chunkId=456` — 当前选中的分块

这样刷新页面或分享链接都能恢复到同一位置。

## 四、摘要生成

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/rag/RagService.java`、`MaterialSummaryEntity.java`
> 📄 **前端文件**：`frontend/src/components/workspace/SummaryPage.tsx`

### 4.1 功能说明

用户可以为每份资料生成 AI 摘要，快速了解资料的核心内容。当前摘要是通用结构化设计，不再假设所有资料都是教材；报告、会议纪要、产品文档、网页资料也可以按同一套流程整理。

### 4.2 实现流程

```
用户点击"生成摘要"
  → POST /api/rag/summarize { materialId, summaryType }
  → 后端按章节/标题聚合全量 chunk，压缩成结构化概览
  → 扫描版 PDF 或文本不可抽取资料会附带页面图片给多模态模型
  → 发送给 LLM，提示词要求只返回 JSON：
     - summary：总览文本
     - sections：核心摘要、关键要点、结构脉络、风险限制、后续行动等区块
  → LLM 返回结构化摘要；如果返回不是 JSON，后端使用本地规则兜底
  → 存入 material_summary 表
  → 前端显示摘要区块、来源定位和用户整理版编辑框
```

### 4.3 历史版本

每次生成摘要都会保存一个新版本。前端显示最新摘要，下方展示历史版本时间线。

### 4.4 来源跳转与整理版

结构化摘要会保存 `sources_json`，每条来源包含 `materialId`、`chunkId`、`pageNo`、`chunkIndex` 和摘录。用户点击来源后会跳转到阅读器，并带上 `materialId`、`chunkId`、`pageNo` 和 `view=smart`，让阅读器尽量定位到对应页和片段。

右侧"我的整理版"保存到 `user_note` 字段，适合用户在 AI 摘要基础上改成自己的笔记。它不会覆盖 AI 原摘要，历史摘要也仍然可以追溯。

## 五、评估系统

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/rag/EvaluationService.java`、`EvaluationSuiteService.java`、`EvaluationScheduler.java`
> 📄 **前端文件**：`frontend/src/components/workspace/EvaluationPage.tsx`

### 5.1 为什么需要评估？

RAG 系统的回答质量取决于很多因素：分块策略、检索算法、提示词、模型选择等。手动一个个测试效率太低，评估系统可以批量自动化测试。

### 5.2 评估套件

一个评估套件（Suite）包含多个测试用例（Case）：

```
测试用例：
  问题："TCP 三次握手的过程是什么？"
  材料范围：《计算机网络》
  答案必须包含：["SYN", "SYN+ACK", "ACK", "三次"]
  来源必须命中：["三次握手", "连接建立"]
```

### 5.3 评估流程

```
1. 对每个测试用例：
   a. 执行完整 RAG 流程（检索 + 生成）
   b. 用 LLM 自动评分：
      - Faithfulness（忠实度）：回答是否忠实于检索到的资料
      - Context Relevance（相关度）：检索到的资料是否与问题相关
      - Overall（综合评分）
   c. 检查答案是否包含预期关键词（answerCoverage）
   d. 检查来源是否命中预期关键词（sourceCoverage）
   e. 综合判定 PASS 或 FAIL

2. 汇总结果：
   - 通过率 = PASS 数 / 总数
   - 平均忠实度、相关度、综合分数
   - 每个用例的详细结果和缺失关键词
```

### 5.4 定时回归

评估套件可以设置定时运行（1-720 小时一次）。后端有一个调度器，按配置的间隔自动运行套件，记录历史结果。

### 5.5 前端评估工作台（EvaluationPage）

三栏布局：

```
┌──────────────┬────────────────────┬────────────────────┐
│  已保存套件列表 │   套件配置（用例编辑） │   结果展示          │
│  (左侧)       │   (中间)            │   (右侧)            │
└──────────────┴────────────────────┴────────────────────┘
```

- **左侧**：已保存的套件列表，显示通过率徽章
- **中间**：编辑用例（问题、材料范围、预期关键词），设置定时回归
- **右侧**：四个指标卡片（通过率/忠实度/相关度/综合分），每项结果详情，运行历史

两种运行模式：
- **即时运行**：不保存，直接测试当前编辑的用例
- **保存后运行**：保存为套件，可重复运行和定时回归

## 六、对话管理

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/rag/RagQuestionRepository.java`、`RagQuestionSourceRepository.java`、`FavoriteService.java`
> 📄 **前端文件**：`frontend/src/lib/chat-session.ts`、`frontend/src/components/workspace/HistoryPage.tsx`、`FavoritesPage.tsx`、`ChatHistory.tsx`

### 6.1 对话持久化

每次问答都会保存到 `rag_question` 表，包括：
- 问题文本、回答文本
- 使用的模型名
- 对话 ID（同一组对话共享 `conversation_id`）
- 来源引用（`rag_question_source` 表）
- 问题附带的图片 JSON（`question_images_json`，用于历史回显）
- 问题附带的临时资料 JSON（`question_temporary_material_json`，用于历史回显）

历史详情接口会把数据库中的每一行问答拆成两条消息：

```
rag_question 一行
  ├─ user 消息：question_text + images + temporaryMaterial
  └─ assistant 消息：answer_text + sources
```

这样前端 `ChatThread` 可以统一按消息流渲染，不需要知道数据库里“一行同时包含问题和回答”的结构。

### 6.2 对话 ID 机制

```
第一个问题：conversation_id = 自己的 id（如 100）
后续问题：conversation_id = 第一个问题的 id（100）
这样所有相关问题都归为一组
```

### 6.3 多轮对话上下文

发送问题时，前端会附带最近 10 条历史消息（5 轮对话）：

```json
{
  "question": "它的优缺点是什么",
  "conversationHistory": [
    { "role": "user", "content": "什么是TCP" },
    { "role": "assistant", "content": "TCP是..." },
    { "role": "user", "content": "它有什么特点" },
    { "role": "assistant", "content": "TCP的特点..." }
  ]
}
```

后端将这些历史拼接后一起送给 LLM，让 AI 知道上下文。

### 6.4 前端状态管理

聊天状态使用 External Store 模式（`chat-session.ts`），通过 `useSyncExternalStore` 订阅：

```
状态结构：
{
  messages: ChatMessage[],           // 消息列表
  conversationHistory: [],           // 多轮上下文
  streaming: boolean,                // 是否正在流式输出
  mode: 'GENERAL' | 'MATERIAL',     // 问答模式
  materialId: string | null,         // 绑定的资料
  conversationId: string | null,     // 当前对话 ID
  images: ChatImagePayload[],        // 待发送图片
  temporaryMaterial: TemporaryMaterial | null, // 通用问答临时资料
  chunkId: string | null,             // 阅读器或资料问答当前片段
}
```

#### 三层持久化

| 层级 | 存储位置 | 用途 |
|------|---------|------|
| 当前草稿 | `sessionStorage` | 刷新页面保持状态 |
| 草稿备份 | `localStorage` | 标签页关闭后恢复 |
| 对话归档 | `localStorage`（按对话 ID） | 从历史恢复完整对话 |

临时资料正文可能很长，写入浏览器存储前会压缩到 2 万字以内；文件名、大小、类型等元数据仍保留，历史消息可以正常显示附件卡片和预览提示。

#### 崩溃恢复

如果流式输出过程中页面被刷新：
- 有部分文本 → 附加"流被页面刷新中断，已恢复部分回答"
- 没有文本 → 标记错误"流被页面刷新中断，请重新发送问题"

### 6.5 收藏功能

用户可以收藏某个问答（`user_favorite` 表），收藏列表在独立页面展示，方便回顾。

### 6.6 历史记录页面（HistoryPage）

- 搜索：按问题/回答文本过滤（300ms 防抖）
- 批量操作：多选删除
- 操作：收藏/取消收藏、查看详情、删除、置顶
- 点击历史条目跳转到聊天页面，恢复完整对话

### 7.1 功能说明

| `id` | 配置 ID |


### 7.4 配置管理流程

**添加配置**：用户填写 displayName、baseUrl、apiKey、model → 后端校验 → 保存并设为 active。

### 7.5 底层调用机制

当用户激活了自定义模型后，`ThirdPartyLlmClient` 会自动切换：
```
if (用户有激活的自定义配置) {
    创建新的 LlmClient（自定义 baseUrl、apiKey、model）
} else {
    使用系统默认的 LlmClient
}
```

**使用限制豁免**：激活自定义模型的用户不受每日 100 条的对话限制（因为消耗的是用户自己的 API 额度）。

## 九、LLM API 双格式支持

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/llm/LlmClient.java`（接口）、`OpenAiCompatibleLlmClient.java`（Chat Completions + Responses）、`ThirdPartyLlmClient.java`（第三方适配）

### 9.1 为什么需要双格式？

OpenAI 有两种 API 格式：
- **Chat Completions API**（`/v1/chat/completions`）：传统格式，所有模型供应商都兼容
- **Responses API**（`/v1/responses`）：较新格式，请求体和响应体结构不同

此外，还兼容 Anthropic Messages API 格式（当 baseUrl 包含 `/anthropic` 路径时）。

### 9.2 配置方式

通过 `LLM_API_FORMAT` 环境变量控制：

```yaml
app:
  llm:
    api-format: chat-completions   # 或 "responses"
```

### 9.3 响应解析差异

| API 格式 | 内容获取路径 | Token 字段 |
|----------|------------|-----------|
| Chat Completions | `choices[0].message.content` | `usage.prompt_tokens` |
| Responses | `output_text` | `usage.input_tokens` |
| Anthropic | `content[].text` | 估算 |

流式 SSE 事件的解析也各有不同，`OpenAiCompatibleLlmClient` 自动根据格式选择解析方法。

## 十一、安全加固

> 📄 **后端文件**：`backend/src/main/java/com/mytext/learningassistant/security/` 目录（`ShortTermStateStore.java`、`InMemoryStateStore.java`、`RedisStateStore.java`、`RateLimitService.java`、`SecurityHeadersFilter.java`、`OutboundUrlGuard.java`）

本项目采用多层安全机制保护后端服务。

### 11.1 接口限流（Rate Limiting）

#### 为什么需要限流？

防止恶意用户通过暴力破解密码、频繁发送请求等方式攻击系统。限流可以：
- 保护登录接口：防止暴力破解密码
- 保护注册接口：防止批量注册垃圾账号
- 保护验证码接口：防止恶意消耗邮件资源
- 保护 RAG 接口：防止滥用 AI 资源

#### 限流实现

`RateLimitService` 使用**滑动窗口算法**，按 IP 或用户维度统计请求次数：

```java
// 限流配置示例
app.security.rate-limit.login-per-minute=10        // 每分钟最多 10 次登录尝试
app.security.rate-limit.register-per-minute=10     // 每分钟最多 10 次注册
app.security.rate-limit.email-code-per-minute=6    // 每分钟最多 6 次验证码请求
app.security.rate-limit.rag-chat-per-minute=30     // 每分钟最多 30 次问答
```

#### 策略模式：ShortTermStateStore

限流需要存储每个 IP/用户的请求时间戳列表。本项目使用**策略模式**，支持两种存储后端：

```
ShortTermStateStore（接口）
    ├── InMemoryStateStore（内存实现）
    └── RedisStateStore（Redis 实现）
```

**InMemoryStateStore — 内存实现**
- 使用 `ConcurrentHashMap` 存储
- 优点：零依赖，启动即用
- 缺点：重启后数据丢失，多实例不共享
- 适用：本地开发、单实例部署

**RedisStateStore — Redis 实现**
- 使用 Redis 存储，自动过期
- 优点：多实例共享状态，数据持久化
- 缺点：需要 Redis 服务
- 适用：生产环境多实例部署

#### 如何选择？

通过 `app.redis.enabled` 配置开关自动切换：

```yaml
app:
  redis:
    enabled: false   # 使用内存实现（默认）
    enabled: true    # 使用 Redis 实现
```

Spring Boot 根据配置自动注入对应的实现类，`RateLimitService` 无需关心底层细节。

#### 限流触发后的响应

当请求超过限制时，后端返回 HTTP 429（Too Many Requests）：

```json
{
  "code": 429,
  "message": "请求过于频繁，请稍后再试",
  "data": null
}
```

### 11.2 登录验证码（Login Captcha）

连续登录失败 5 次后，系统强制要求输入图形验证码，防止暴力破解：

```
用户连续失败 5 次
  → 后端标记该 IP+用户名 需要验证码
  → 前端显示验证码输入框
  → 用户输入验证码
  → 后端验证通过后才允许登录
```

### 11.3 HTTP 安全响应头

`SecurityHeadersFilter` 自动为所有 HTTP 响应添加安全头：

| 响应头 | 作用 |
|--------|------|
| `X-Content-Type-Options: nosniff` | 防止浏览器猜测文件类型 |
| `X-Frame-Options: SAMEORIGIN` | 防止页面被嵌入 iframe（点击劫持防护） |
| `Content-Security-Policy` | 限制资源加载来源（XSS 防护） |
| `Strict-Transport-Security` | 强制 HTTPS（仅在 HTTPS 环境生效） |

### 11.4 SSRF 防护

`OutboundUrlGuard` 在网页导入功能中校验用户提交的 URL：

```
用户提交 URL: http://192.168.1.1/admin
  → 校验是否为内网地址？
  → 是 → 拒绝请求，返回 400 错误
  → 否 → DNS 解析后再次校验
  → 解析结果是内网？→ 拒绝（防止 DNS 重绑定攻击）
  → 通过 → 允许访问
```

阻止的地址类型：
- `localhost`、`127.0.0.1`、`0.0.0.0`
- 内网地址（`10.x.x.x`、`172.16-31.x.x`、`192.168.x.x`）
- 云元数据地址（`metadata.google.internal`、`169.254.169.254`）

### 11.5 Token 版本失效

当用户执行以下操作时，`tokenVersion` 自增，所有旧 Token 立即失效：

- 修改密码
- 重置密码（邮箱验证码重置）
- 登出

```
用户修改密码
  → user.tokenVersion++（从 0 变为 1）
  → 旧 Token 中的 tokenVersion=0
  → AuthInterceptor 验证时发现不匹配
  → 返回 401 Unauthorized
```
